# Problem Scoping Studio

> Step 28 loads the scoped problem, intended users, users not served well, boundaries, error impacts, and human responsibilities as immutable evidence links.

Purpose: define a need before selecting technology. The mandatory Step 21 pre-build gate asks exactly: What problem are we addressing? Who experiences the problem? Who was consulted? What happens without this tool? Why might AI help? Could a simpler non-AI solution work? What information would the tool need? What could go wrong? Who would be affected by an error? Who remains responsible?

Unresolved critical questions block workflow design and prototyping. This static prototype models the gate but has no production server, import, or offline-sync enforcement.

## System-card relationship

The current student-confirmed Step 22 scope supplies the card’s problem and user boundaries; scope changes mark the card stale.

## Architecture mapping

Every architecture component and requested data item must map to the current Step 22 scope. Scope changes mark the architecture stale and require a new version.

## Data-purpose mapping

Every proposed data item must be necessary for the current scoped task; scope or purpose changes make the linked Data Plan stale.

## Fairness mapping

Affected, intended, indirectly affected, unsupported, and error-burden users from the current scope seed the Fairness Scenario Matrix. Changed users or scope make the evaluation stale.

## Iteration scope

Changes remain within the current Step 22 scope. New users, purposes, high-stakes functions or substantially different systems require rescoping before a new prototype version.
